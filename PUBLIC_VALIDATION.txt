**Method**

Two versions × two destination scenarios × three repeats = 12 fresh Python worker processes, using the public `resolve_source_to_path()` API. Each worker checked its imported module path and source SHA. The source PDF was at the same Chinese-containing path throughout. `ascii-explicit` used an ASCII destination root and an explicit `workdir`; `cjk-automatic` used `workdir=None` with the temporary-directory environment pointed at a Chinese-containing destination root. These are destination scenarios, not a complete input/output character-set matrix.

Imports and the initial input hash completed before measurement. `tracemalloc` and elapsed-time measurement surrounded the resolver call. Copy hashing, mutation and cleanup happened afterwards. The parent sampled the actual worker PID's Windows working set, with the pre-call, post-import/post-hash working set as the baseline. It requested a 5 ms interval; the largest observed sampling gap was 16.2455 ms. The sampling window includes a small process-communication boundary and can miss short-lived peaks.

Source, test, configuration and harness hashes, plus dependency-version snapshots, were checked before and after the entire matrix and remained unchanged.

**Per-run measurements**

Memory columns are bytes. “WS increase” is sampled working-set peak minus that worker's post-import baseline, not total process memory. Times are descriptive, rounded to six decimals; `results.json`/`results.csv` retain the original numeric values. The initial hash read warms the input cache. These instrumented, warm-cache runs are not a throughput benchmark.

**Content and lifetime checks: 12/12 passed**

Every returned copy existed after the API returned, had the expected filename/directory, and matched the input's size and SHA-256. Each was a different file (`samefile` was false). Each worker modified and truncated only its returned copy and checked that the original's content and modification time were unchanged. It then explicitly deleted that copy and its owned empty directory and checked that the original remained intact. The final wrapper also checked the original's size, SHA-256 and modification time after all 12 runs. Cleanup did not recursively delete directories. “Ownership” here means independent file lifetime, not preservation of ACL/owner metadata.

**Verified pytest command shape (PowerShell, from the repository root)**

These commands reproduce the regression-test selection, not the parent-process RSS sampling harness. This bundle contains measured results and the method, and does not claim to include a separately validated portable benchmark runner.

**Scope and limits**

- This measures public file-copy/staging I/O only, not PDF parsing, OCR or end-to-end conversion. One real file size and three repeats per scenario do not establish a general speedup or an all-input memory bound.
- Successful temporary copies still occupy full disk space and remain the caller's responsibility. This does not solve the disk-quota problem in #185.
- The bounded-copy path applies to new local destinations. Existing destinations retain the buffered read-before-write behavior; URL handling retains its existing buffering.
- Error cleanup is best-effort: OS denial can leave a file/directory. Cleanup warnings preserve the original I/O exception. Explicit workdirs are not removed and may remain empty after a failed call. No crash/power-loss or actual full-disk experiment was performed.
- `tracemalloc` does not cover all native allocations. Sampled working-set increases are neither total process memory nor operating-system lifetime peaks.
- Linux/macOS, privileged Windows symlink handling, and the complete repository/all-extras CI suite were not run.
